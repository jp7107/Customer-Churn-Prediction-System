### 3.1 Dataset acquisition and integrity

1. Use the IBM Telco Customer Churn dataset from the Kaggle source specified above. Support the common filename `WA_Fn-UseC_-Telco-Customer-Churn.csv`; also allow a clearly configured local CSV path.

3. Record the source URL, local filename, acquisition date if known, file hash, row count, column count, and target distribution in a data provenance report. Do not invent acquisition metadata.
4. Validate the actual file before training. Check required columns, target existence, valid target labels, duplicate rows, duplicate customer identifiers, data types, missingness, and unexpected categories.
5. The commonly distributed dataset contains 7,043 rows and 21 columns, with `Churn` as the Yes/No target. Treat these as **sanity-check expectations**, not values to force. Report actual values read from the downloaded file and investigate any mismatch.
6. The commonly distributed file includes `TotalCharges` stored as text, with blank strings in some records (commonly associated with customers whose `tenure` is zero). Convert it safely to numeric. Inspect the actual blank rows and document the treatment. A defensible rule is to set `TotalCharges` to zero only where the blank is consistent with `tenure == 0`; handle any other missing values using a training-fitted imputer. Do not silently drop those records.
7. Treat values such as `No internet service` and `No phone service` as meaningful categorical values, not as missing values.
8. Remove `customerID` from model predictors. It is an identifier, not a customer-behavior feature. Keep it only for record traceability where appropriate, and never use it as a predictive feature.
9. Detect exact duplicate rows and repeated customer IDs separately. Do not remove records without recording the count and the documented decision. Do not assume every repeated ID is a harmless duplicate.

### 3.4 Preprocessing architecture — leakage-safe by construction

The production training path must use Scikit-learn `Pipeline` and `ColumnTransformer` (or an equally rigorous pipeline abstraction) so all learned preprocessing is fit only on the training fold.

Required safeguards:

1. Split off the final holdout test set **before** fitting imputers, encoders, scalers, feature selectors, resamplers, or tuning thresholds.
2. Use a stratified split because the target classes are imbalanced. A reasonable starting point is 80% train / 20% test with a fixed random seed such as `42`; document any justified alternative.
3. Use only the training portion for cross-validation, model selection, hyperparameter tuning, class-weight selection, and threshold selection.
4. Do not inspect test performance repeatedly while making model or threshold decisions. The holdout test set is for one final evaluation after decisions are frozen.
5. Fit numeric and categorical preprocessing independently inside each cross-validation fold through the estimator pipeline.
6. Use `OneHotEncoder(handle_unknown="ignore")` for nominal categorical columns so unseen categories at inference do not crash the model.
7. Use training-fitted imputation. A typical starting strategy is median imputation for numeric features and most-frequent imputation for categorical features. Document exceptions.
8. Scale numeric data for Logistic Regression. Scaling is not generally necessary for Random Forest or tree boosting. Use model-specific pipelines when preprocessing differs.
9. Preserve the distinction between a true missing value and a meaningful category such as `No internet service`.
10. Never apply SMOTE, oversampling, undersampling, imputation, scaling, or feature selection to the complete dataset before splitting. If resampling is explored, it must run only inside each training fold using an imbalanced-learn pipeline.

The `TotalCharges` special case must be implemented consistently in both training and inference. Prefer a small, tested preprocessing transformer or shared pure function; do not perform the correction only in a notebook.

- Other billing or service-combination features only when they are mathematically valid, available at prediction time, and supported by EDA.

### 3.7 Cross-validation and hyperparameter optimization

- Use `StratifiedKFold` (a reasonable starting point is 5 folds, shuffled, fixed random seed) on the training portion.
- Use cross-validation for comparing candidates and tuning a restrained, computationally sensible search space.
- Prefer `RandomizedSearchCV` or a small, justified `GridSearchCV` with explicit scoring, reproducible seed, and `n_jobs` set safely for the environment.
- Consider ROC-AUC and average precision / PR-AUC during development. Given the churn class imbalance, do not optimize accuracy alone.
- Keep the hyperparameter search bounded so the complete project remains runnable within the assessment window and on an ordinary laptop.
- Store complete cross-validation results, best parameters, scorer definition, fold configuration, and random seeds in machine-readable form.
- Do not tune using the holdout test set.

### 3.8 Class imbalance strategy

- Establish a no-resampling baseline.
- Evaluate class-sensitive approaches such as `class_weight="balanced"` for Logistic Regression / Random Forest and an appropriately calculated `scale_pos_weight` for XGBoost. Calculate any ratio using training data only.
- Do not assume SMOTE is automatically superior. For one-hot categorical data, synthetic interpolation can create invalid fractional category patterns. If SMOTE is tested, explain the encoding strategy and apply it inside each training fold only.
